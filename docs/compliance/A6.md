## Design explanation

### New module: `optimizer/simulation.py`

A6 adds `apply_changes` and `diff_results`.

**`apply_changes(scenario, changes) → Scenario`**

- Applies a list of typed `Change` objects to a **deep copy** of the scenario. The original is never mutated (verified by tests).
- **Allowlisted paths only** — no `eval`, no arbitrary JSON path access:
  - `capacity` → `business.capacityMinutes`
  - `coordination` → `business.coordinationMinutes`
  - `estimate` → `business.estimates[service].minutes` (adds the estimate if the service isn't present)
- **Atomic validation** — all changes are validated *before* any are applied. If any change is invalid, `SimulationError` is raised and the original is untouched. No partial application.
- **Duplicate target rejection** — the same `(kind, businessId)` or `(estimate, businessId, service)` target may not appear twice.
- **Strict numeric/ID validation** — unknown `businessId` rejected; capacity/coordination ≥ 0; estimate minutes ≥ 1.
- **No language parsing** — this function never calls Bedrock or interprets text. Natural-language interpretation is the backend's job (B6); it must convert text to explicit `Change` objects first.
- After applying, the patched scenario is **re-validated through Pydantic** so `extra=forbid` and all schema invariants are re-enforced.

**`diff_results(before, after) → ResultDiff`**

- Compares two `Result` objects and returns a `ResultDiff` with per-business deltas and aggregate totals deltas.
- Does **not** change the `Result` wire schema — `ResultDiff` is an internal helper type for the backend `/simulate` response and the UI.
- Handles all status combinations (collaboration / no_exchange / infeasible), including transitions where `totals` go from populated to `None`.
- `improved` / `degraded` properties summarise whether the change helped.

### Why deep-copy via JSON round-trip

`json.loads(scenario.model_dump_json())` produces a fully independent nested dict with no shared references to the original's lists/objects. Mutating the copy cannot affect the original. Re-validating through `Scenario.model_validate` guarantees the output is a well-formed scenario.

### The solver is not called here

`apply_changes` returns a patched `Scenario`. The caller (backend B6) runs `optimize()` on it. This keeps the mutation logic and the solving logic cleanly separated and independently testable.

## Input / output / error data flow

```
POST /simulate (B6 backend)
  apply=true, explicit changes:
    → apply_changes(scenario, changes)   [A6 — atomic, allowlisted]
        → deep copy → validate → apply → re-validate
        → patched Scenario
    → optimize(patched)                  [A2]
    → diff_results(original_result, patched_result)  [A6]
    → SimulateResponse(scenario=patched, result=patched_result, ...)

  text provided (apply=false):
    → backend interprets text via Bedrock → produces proposed Change[]
    → apply_changes is NOT called until user confirms (two-stage)

Errors:
  SimulationError → backend maps to 422 VALIDATION_ERROR with fields
```

---

## Algorithm assumptions and complexity

1. Changes are already typed `Change` objects (Pydantic-validated by the backend before reaching `apply_changes`).
2. The deep copy via JSON round-trip is O(scenario size) — trivial at MVP scale (≤5 businesses, ≤6 deliverables).
3. `apply_changes` does not run the solver; complexity is linear in the number of changes.
4. `diff_results` is O(number of businesses).
5. All arithmetic is integer minutes; no floats.

## AWS responsibilities

None. Pure Python. The backend (B6) is responsible for the Bedrock call that interprets natural-language text into `Change` objects — that call never happens inside `apply_changes`.

## Judge questions

**Q1: How do you prevent a malicious or malformed change from corrupting the scenario?**  
A: Three layers. First, changes are typed `Change` Pydantic models — the backend rejects malformed JSON before they reach `apply_changes`. Second, `apply_changes` uses an explicit allowlist of three change kinds mapped to specific fields — there is no `eval` or arbitrary path access, so a change can only ever touch capacity, coordination or an estimate. Third, all changes are validated before any are applied, so an invalid change in the list causes atomic rejection with the original untouched.

**Q2: Why does `apply_changes` not run the solver itself?**  
A: Separation of concerns. `apply_changes` produces a patched scenario; `optimize` solves it. Keeping them separate means each is independently testable, and the backend can choose whether to run the solver (apply=true) or just propose the change (apply=false, two-stage confirmation). It also means the what-if engine has zero coupling to the solver's internals.

**Q3: Why is natural-language parsing explicitly excluded from this module?**  
A: The contract requires a two-stage simulate flow: propose (via Bedrock) then confirm/apply (deterministic). Mixing language interpretation into the deterministic apply step would make the engine non-deterministic and untestable. By requiring explicit `Change` objects, `apply_changes` stays fully deterministic — the same input always produces the same output, which is essential for the certificate and for reproducible demos.
