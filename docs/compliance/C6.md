## Data flow

Stage 1, text: `propose` sends `{scenario: confirmed, changes: [], text, apply: false}`. The response's `proposedChanges` are checked by `checkChanges` against the confirmed scenario: allowlisted shapes only, no extra keys, known business ids, integer minutes in range (estimate >= 1, others >= 0, <= 1,000,000), no field changed twice, at most 20. Any violation rejects the whole proposal with an error and nothing is offered for approval. An empty proposal is a notice. Any `result` in a proposal response is ignored, never shown.

Review: the proposal panel lists each change as "DesignCo design estimate: 3 h → 10 h" (old value read from the confirmed scenario) under "NOT applied yet". Manual changes enter the same panel (`addManual`, using the C2 duration rules; sub-minute and zero estimates rejected). Nothing is sent for manual input before approval.

Stage 2, approval: `apply` sends `{scenario: confirmed, changes: <exactly the reviewed list>, apply: true}` with no `text`. The response is accepted only if: mode matches (C1), `result` is non-null, and `response.scenario` equals `applyChanges(confirmed, approved)` (compared by `sameScenario`, ignoring the order of estimates). Otherwise it is discarded with an error. On success the reducer stores `{changes, scenario, result, mode}` as `whatIf` beside the unchanged `confirmed` and `result`.

Display: `WhatIfResult` shows the changes applied, status, reasons (so infeasibility is visible), a comparison table (original vs what-if, "n/a (infeasible)" for null totals), an assignment diff from `compareAssignments`, then the same graph, savings and certificate components applied to the what-if scenario. Nothing is animated or inferred; every cell comes from a result.

Errors: network/envelope/shape/mode problems show an alert. A failed proposal keeps the description. A failed apply keeps the reviewed changes so the user can retry or cancel; nothing is applied.

Staleness: a `seq` counter plus `AbortController`. An effect on `version` (any edit to the inputs) aborts, clears the proposal and bumps `seq`; "Cancel" does the same while a request is pending. A late response whose id is not current is dropped. The reducer additionally refuses `set_whatif` for an older version or without a base result.

## Assumptions and limits

- The browser applies the approved changes itself only to cross-check the server's scenario; it never computes assignments or savings.
- Rejecting duplicate fields and any extra keys is stricter than the schema requires. A real model that proposes two changes to one field will be rejected rather than guessed at.
- The scenario cross-check assumes the backend returns exactly base + changes. If B6 returns additional normalization, this check needs a joint decision rather than loosening.
- `proposedChanges` in the apply response is not compared with what was sent; the scenario comparison is the check.
- A what-if cannot be promoted to a new base; the user edits the inputs instead.
- Complexity: O(changes x businesses), at most 20 changes and 3 businesses.

## Judge questions

1. Can the model change the scenario by itself? No. Text goes out with `apply=false` and no changes. Only a list that passes the allowlist check and that the user approves is sent with `apply=true`, and the returned scenario must equal base + that list or it is discarded.
2. Why keep the original? The what-if is computed on a copy; the confirmed scenario, its result and certificate stay on screen so the difference is visible, and the label says which input version the copy came from.
3. Is designco design = 10 h "infeasible"? No. Self-production remains valid, so the status is no_exchange; only all-zero capacities give infeasible. The UI reads the status from the result and draws no exchange arrows for no_exchange.
4. What if an old reply arrives late? Edits and Cancel bump a request id and abort; a reply with an old id is dropped, and the reducer also rejects a what-if for an older input version.
