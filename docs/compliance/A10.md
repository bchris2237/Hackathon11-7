## Design explanation

### New module: `optimizer/risk.py`

A10 adds `evaluate_risk` — **sensitivity analysis, explicitly not probability.**

**`evaluate_risk(scenario, perturbations) → RiskReport`**

- `perturbations` is a finite, explicit list of `PerturbationScenario` objects, each a named bundle of `EstimatePerturbation`s (businessId, service, new integer minutes).
- The **nominal** (zero-perturbation) result is computed once; its certificate is preserved in the report **unchanged** — risk analysis never mutates or re-signs the certified nominal result.
- For each perturbation: convert to `EstimateChange`, apply to a deep copy via A6 `apply_changes` (original never mutated), rerun the solver, record the observed status and net savings.
- Invalid perturbations (unknown business, bad service) are recorded as `rejected` — never raised.

### Sensitivity, not probability

The report's `note` states plainly: no distribution is assumed, no confidence level is implied, and `worst_net_savings` is the worst **observed** outcome among the **tested** perturbations — not a bound over all possible perturbations. This is the single most important honesty constraint in A10 and is enforced by a dedicated test (`test_note_disclaims_probability`).

### Integer-only perturbations

`EstimatePerturbation.new_minutes` is an explicit integer. The caller computes any percentage change into an integer before passing it, so there is zero floating-point rounding inside the model. This keeps every rerun deterministic and consistent with the frozen integer-minutes contract.

### Core objective preserved

`evaluate_risk` does not change the objective (minimise effort, no-worse-off). Each rerun uses the unchanged solver. The nominal certified result is untouched.

## Input / output / error data flow

```
Caller (backend or analysis tool)
  → evaluate_risk(scenario, perturbations)
      → nominal = solve(scenario)        [certificate preserved unchanged]
      → for each perturbation:
            EstimatePerturbation → EstimateChange
            apply_changes(scenario, changes)   [deep copy, A6]
            solve(patched)                     [rerun]
            record PerturbationOutcome
  → RiskReport

Errors: invalid perturbations recorded as rejected outcomes; never raised.
Original scenario and nominal certificate never mutated.
```

## Algorithm assumptions and complexity

- O(perturbations × solve_cost). Each solve is ≤15 625 candidates.
- No probability model, no sampling, no distribution. Finite explicit set only.
- All perturbation values are integers; no float rounding.

## Judge questions

**Q1: Is this a risk score or a probability?**  
A: Neither — it is sensitivity analysis. We rerun the solver for a finite set of explicit, user-chosen perturbations and report what each actually produced. There is no assumed probability distribution over estimate errors, so we deliberately make no "X% chance of infeasibility" claim. The worst figure reported is the worst observed among the tested cases, explicitly not a bound over all possible changes.

**Q2: Does running risk analysis change the certified result?**  
A: No. The nominal result is computed once and its certificate is preserved in the report exactly as issued. Every perturbation is applied to a deep copy, so the original scenario and its certificate are never mutated or re-signed. A test confirms the nominal certificate digests match a fresh optimize of the unperturbed scenario.

**Q3: Why are perturbation values explicit integers rather than percentages?**  
A: The whole model is integer minutes with no floating-point feasibility arithmetic. If we accepted "20% higher" we'd introduce rounding ambiguity. By requiring the caller to pass an explicit integer new value, every rerun is deterministic and consistent with the frozen contract. The caller owns any rounding decision transparently.
