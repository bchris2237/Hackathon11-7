## What B3 delivers

`backend/confirmation.py: validate_scenario` adds the rules that JSON Schema and the generated Pydantic models cannot express, because they
compare parts of a scenario with each other. `confirm_scenario` runs them and returns the scenario unchanged.

| Rule | Where it comes from | Result |
|---|---|---|
| Required fields, no `null`, whole non-negative minutes up to 1,000,000, positive estimates, frozen service list, exactly 3 businesses, 1 to 6 deliverables, `confirmed` is `true`, no unknown fields | Schema / generated models (already existed) | 422 `VALIDATION_ERROR` |
| Business ids unique, deliverable ids unique | **B3** | 422 `VALIDATION_ERROR` |
| Every deliverable's `ownerId` is a business in this scenario (no unknown or invented ids) | **B3** | 422 `VALIDATION_ERROR` |
| At most one estimate per service per business | **B3** | 422 `VALIDATION_ERROR` |
| Each owner has an estimate for the service it needs itself (its baseline) | **B3** | 422 `MISSING_BASELINE` |
| Valid but cannot work out (all capacities 0; baseline above capacity) | Not rejected | Accepted. It is the optimizer's `infeasible`, not malformed input |

Before B3 the schema accepted five invalid scenarios (duplicate business ids, duplicate deliverable ids, unknown owner, duplicate service estimate,
missing own baseline). That was verified by running them, not assumed.

## Design and tradeoffs

| Decision | Why | Tradeoff |
|---|---|---|
| One function, `validate_scenario`, used by `/confirm` and `/optimize` (hooked in `App._check_request_rules`) | The two routes cannot disagree about what a valid scenario is. Invalid input never reaches the optimizer | `/simulate`, `/explain`, `/certificates` and `/profiles` also take a scenario and must call it when they are built. They are unwired (503) today |
| Consistency problems are reported before baseline problems | A dangling `ownerId` makes "missing baseline" meaningless, so fix structure first | A user with both problems sees them in two rounds |
| `/confirm` returns exactly what it validated: no sorting, rounding or filling in | The response is the client's own data, so there is nothing for the server to get wrong and the digest later computed from it is predictable | "Normalization" here means strict validation into the one canonical wire shape, not rewriting |
| Missing baseline is its own code, `MISSING_BASELINE`, with field paths like `scenario.businesses[2].estimates.coding` | The frozen contract names it. A UI can show "fill in coding time for CopyCo" | |
| Valid-but-infeasible input is accepted | The contract separates malformed input from an infeasible scenario | A scenario that can never work passes `/confirm`; the optimizer says so later |
| `confirm_scenario` has no authentication and its response claims nothing about who confirmed | `confirmed: true` is a flag any client can send. The control is the UI workflow (review the draft, fill the gaps, press confirm) | A scripted client can "confirm" anything that is complete and consistent |
| Error `fields` now use one path style, `a.b[0].c`, on every 422 (changed B1's dotted `a.b.0.c`) | `/extract`'s `missingFields` and B3's paths already used brackets, so a UI would otherwise need two parsers. Found while testing B3 | A visible change to the text of schema-error `fields`. **Tell Developer 3** |
| Messages are fixed text; paths contain names and indexes, never values | Business names and descriptions can be private (tested with a marker string) | Less detail than a value-echoing message |

## Data flow (input to output to error)

1. `backend/app.py: App._dispatch`: route, size, adapter present, JSON parse, `model_validate` (all B1). Failure: 400 / 413 / 422 `VALIDATION_ERROR` (schema paths).
2. `App._check_request_rules` calls `validate_scenario` for `ConfirmRequest` and `OptimizeRequest`. Failure: 422 `VALIDATION_ERROR` (consistency) or 422 `MISSING_BASELINE`.
3. `backend/confirmation.py: confirm_scenario` validates again (cheap, and safe if called directly) and returns `ConfirmResponse(scenario=...)`.
4. `App._validated_output` checks the response against the contract. `ConfirmResponse` has no `mode`, so there is nothing to mislabel.
5. For `/optimize` the next step is the optimizer adapter (Developer 1), which does not exist in production wiring yet. Until it does the route is 503 before step 2 runs, as B1 specifies. Tests inject a stub adapter and prove it is never reached with an invalid scenario.

## Algorithm assumptions and complexity

- `validate_scenario` makes two linear passes over at most 3 businesses, 9 estimates and 6 deliverables, with set lookups. Constant time in practice.
- Baseline per owner is defined as in the frozen contract (sum of the owner's own estimates for its own deliverables). B3 checks only that each needed estimate exists, and does not compute baselines.
- No floating point anywhere: minutes are integers all the way through.

## Known limits and remaining actions

1. **`confirmed: true` proves nothing about a human.** There is no authentication in this project. Anyone who can reach the API can send a complete, consistent scenario with `confirmed: true`. The guide accepts this for a public demo with fictional data.
2. **`/optimize` is not validated end to end yet.** While no optimizer adapter exists the route answers 503 before validation. The behavior is proven with a stub adapter, and Developer 1's adapter will inherit it automatically through `default_adapters`.
3. **Other scenario-taking routes must call `validate_scenario`** when they are implemented: `/simulate` (also on the patched scenario after a change is applied), `/explain`, `/certificates`, `/profiles`.
4. `Change.businessId` and `Change.service` validity against a scenario is not checked here (simulate prompt).
5. The `fields` text for schema errors changed format (see Design). Developer 3 should check any UI code that parsed the old dotted form (none exists yet in `frontend/`).
6. The 3-business MVP limit is enforced by the schema, not here.
7. No check that capacity is plausible, that baselines fit capacity, or that estimates are reasonable. By design those are the optimizer's job or the human's.

## Judge questions with grounded answers

1. **Why validate in the backend when the form already checks input?** The frontend is not a trust boundary: anyone can call the API directly. Also, JSON Schema cannot compare fields, and five invalid scenarios (duplicate ids, unknown owner, duplicate estimate, missing baseline) passed the schema until B3. They are now rejected and tested, and removing any single check breaks a test.
2. **What does `confirmed: true` actually prove?** Nothing about a person. It is a required flag that a client sets after the UI's review step. The server only guarantees that what arrived is complete and consistent. We say that in the code, the docs and a test that the response claims nothing about a human or identity.
3. **Why is a scenario where every capacity is 0 accepted?** Because it is well formed but cannot work out, which the contract calls `infeasible`, a normal outcome with no allocation, not a malformed request. Rejecting it would turn a legitimate answer into a validation error. A mutation test fails if someone makes it a 422.
4. **Why is a missing own-service estimate an error and not zero?** A missing estimate means the business cannot do that service, never that it is instant. For the owner's own need it also means we cannot compute what doing the work alone costs, so we cannot measure savings. The error names the exact missing estimate so the user can fill it in.
5. **How do you know the same rules protect `/optimize`?** One function is called from one hook for both routes. Tests send each broken scenario to both and assert the optimize adapter's call list stays empty. A mutation that stops validating `/optimize` fails a test.
