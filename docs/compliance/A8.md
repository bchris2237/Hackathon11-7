## Design explanation

### New module: `optimizer/explain.py`

A8 adds `analyze_bottlenecks` and `sensitivity_report`. The governing principle: **every claim is backed by an actual solver rerun** — no estimates, no interpolation, no "minimal repair" promises.

**`analyze_bottlenecks(scenario) → BottleneckReport`**

- Checks for missing baselines first (the solver raises on those, so we detect them before calling it).
- Runs the solver once to get the current status.
- Inspects self-assignment feasibility of each business and reports every binding capacity constraint with the exact excess minutes.
- Explicitly states in `note` that this is observed analysis, not a single-root-cause proof.

**`sensitivity_report(scenario, candidates) → SensitivityReport`**

- `candidates` is a finite, explicit list of `(label, changes)` pairs.
- For each candidate: applies the changes via `apply_changes` (A6), reruns `solve`, and records the resulting status.
- `repaired=True` **only** when a rerun actually produced `collaboration`.
- Invalid patches (e.g. unknown business) are recorded as `valid_patch=False` with a reason — never raised.
- Records `candidate_bound = len(candidates)` so judges can see the search was finite.
- `note` explicitly disclaims any claim about untested changes or global minimum repair.

### Why rerun-based rather than analytical

An analytical "minimum capacity increase" could be wrong if it ignored an interaction (e.g. coordination charges shifting the optimum). By rerunning the actual solver for each explicitly chosen counterfactual, the report can only ever claim what was literally observed. This is honest and defensible to judges.

### No frozen schema changes

`BottleneckReport`, `SensitivityReport`, `TestedCandidate`, `BindingConstraint` are internal dataclasses. The `Scenario`/`Result`/`Certificate` wire schemas are untouched. The backend may serialise these into the `/explain` response text, but the `Result` schema is unchanged.

## Algorithm assumptions and complexity

- `analyze_bottlenecks`: O(businesses + deliverables) plus one solve.
- `sensitivity_report`: O(candidates × solve_cost). Each solve is ≤15 625 candidate evaluations. The caller chooses the candidate list size, keeping the search finite and explicit.
- All arithmetic integer minutes. No probability, no distributions.

## Judge questions

**Q1: How do you avoid falsely claiming a change will fix a scenario?**  
A: `sensitivity_report` never predicts — it applies each candidate change and reruns the actual solver. `repaired=True` is set only when that rerun returns `collaboration`. If a change does not actually repair the scenario, the report shows the real (non-collaboration) status. There is no analytical shortcut that could be wrong.

**Q2: Why don't you claim a "minimum repair"?**  
A: Finding a provably minimal repair would require searching the entire space of possible changes, which we do not do. We test only the finite, explicit candidates the caller supplies and record `candidate_bound`. The report's `note` states plainly that no claim is made about untested changes or minimality. This keeps every statement defensible.

**Q3: How does `analyze_bottlenecks` decide what is a bottleneck?**  
A: It checks each business's self-assignment (owner does its own work, no coordination). If self-production exceeds capacity, that is a binding capacity constraint with a computed excess. Since every feasible allocation must at least allow self-assignment as a fallback, a self-assignment capacity violation is a genuine structural bottleneck. It reports all such observed constraints, not a single "cause".
