## Design explanation

### New module: `optimizer/models.py`

The shared contract (`contracts/models.py`, Developer 2's file) already permits 3–5 businesses and 1–6 deliverables as a **predeclared** optional extension. A9 adds the optimizer-side **gate** that decides whether a >3-business scenario is actually accepted — without touching the shared contract.

- `OptimizerConfig(extended_mode: bool)` — immutable dataclass. `extended_mode=False` (default) → exactly 3 businesses (MVP). `extended_mode=True` → 3–5 businesses.
- `DEFAULT_CONFIG` — the MVP config.
- `validate_scenario_bounds(scenario, config)` — raises `ExtendedModeError` if business count exceeds the config's max, below 3, deliverables outside 1–6, or the exact candidate upper bound exceeds 15 625.
- `candidate_count_upper_bound(scenario)` — exact product of feasible-provider counts per deliverable (≤5^6).

### Gating threaded through solve/optimize

`engine.solve` and `engine.optimize` (and their `solver.py` wrappers) now accept an **optional** `config=None` parameter:
- `config=None` (historical default) → no extended gating; preserves every prior test and all 3-business behaviour.
- `config=OptimizerConfig(extended_mode=True)` → explicit opt-in to 4/5-business mode with the candidate cap enforced.

This design means **no UI or backend file changes are required** to activate extended mode — the backend simply passes a config object. Activation is coordinated, not hard-coded, and three-business defaults are fully preserved.

### Why config-object rather than env var or global

A config object passed per call has no global mutable state, is trivially testable, and lets different requests use different modes concurrently (important for a Lambda handling mixed traffic). No `.env` change is needed.

## Input / output / error data flow

```
POST /optimize (backend)
  → optimize(scenario, config)
      config=None or DEFAULT_CONFIG → MVP (3 businesses)
      config=OptimizerConfig(extended_mode=True) → 3..5 businesses
  → validate_scenario_bounds(scenario, config)   [A9]
      raises ExtendedModeError → 422 VALIDATION_ERROR
  → enumeration + solve (unchanged)

Contract layer (Pydantic) rejects >5 businesses / >6 deliverables at parse time.
A9 gate rejects 4/5 businesses when extended mode is OFF.
```

## Algorithm assumptions and complexity

- Candidate space remains bounded by 5^6 = 15 625 regardless of mode.
- Extended mode does not change the algorithm — it only widens the accepted business count. The same exhaustive enumeration runs.
- `candidate_count_upper_bound` is O(businesses × deliverables).

## Judge questions

**Q1: Does supporting 5 businesses change the correctness guarantees?**  
A: No. The algorithm is unchanged — it still exhaustively enumerates every candidate and checks the same constraints. Extended mode only widens the accepted business count from 3 to 5. The candidate space is still capped at 5^6 = 15 625, and 4/5-business results are cross-checked against an independent brute-force oracle in the tests.

**Q2: Why is extended mode off by default?**  
A: The MVP is scoped to exactly 3 businesses. Keeping extended mode off by default guarantees no existing behaviour changes and no accidental acceptance of larger scenarios. A caller must explicitly pass `OptimizerConfig(extended_mode=True)` — an auditable, deliberate opt-in.

**Q3: What stops this from scaling to arbitrary business networks?**  
A: The hard 5^6 candidate cap. Beyond 5 businesses or 6 deliverables the exhaustive search would exceed 15 625 candidates, and `validate_scenario_bounds` (plus the Pydantic contract) rejects it. Larger networks would require a fundamentally different bounded solver — we explicitly do not claim to solve them.
