## What B1 delivers

One request router that serves both an AWS Lambda behind API Gateway HTTP API (payload format 2.0) and a local server.
Every route is validated the same way. Routes whose real adapter does not exist answer an honest 503. Tests inject
fixture-backed stubs. **Nothing is deployed, and no AWS service has been called.**

## Design and tradeoffs

| Decision | Why | Tradeoff |
|---|---|---|
| One `App.handle(Request) -> Response` used by Lambda and local | Local runs exercise the same code as the cloud, so "works locally" means more | A small Request/Response type to maintain |
| Adapters are injected callables (`Adapters` dataclass); `None` means 503 | Backend is testable before the optimizer or Bedrock exist; no hidden fallback exists to be left wired in | Later prompts must wire adapters in `default_adapters()` |
| Validate with the **generated** Pydantic models | Same contract as the frontend; strict ints/bools reject `600.5`, `"600"`, `true` | The one conditional rule (`text` vs `changes`/`apply`) needs a manual check |
| Fixed error messages; 422 lists field **paths only** | Pydantic's default text echoes input, which could be private business descriptions | Less detail for the client; paths are enough to fix a form |
| `live` mode now starts (changed from Phase 0) | B1 asks for 503s "in live mode", and `/health` must be deployable early to find cloud problems sooner | A live deploy with no adapters is up but useless. Guarded by 503s and by the mode check below |
| Adapter output re-validated; its `mode` must equal the app's mode | A fixture adapter accidentally wired into live would otherwise return simulated numbers labelled real | Costs one extra validation per call |
| Timeout + concurrency cap around adapters | Bedrock calls are slow and cost money; unbounded concurrency means unbounded spend | Abandoned timed-out work keeps its slot until it really ends, so a stuck adapter can cause 429s |
| 32 KiB limit checked before parsing; base64 length checked before decoding | Cheap checks first; API Gateway itself only limits to 10 MB | |
| Local server never reads an over-limit body, rejects chunked and bad `Content-Length`, 10 s socket timeout | Stops a slow or huge client from tying up a thread | `Connection: close` on every response (no keep-alive) |

## Pipeline (input to output to error)

`backend/app.py: App._dispatch`, in this fixed order:
1. `match_route` -> 404 `NOT_FOUND`
2. `OPTIONS` -> 204 with CORS headers only for allow-listed origins
3. method not allowed -> 405 `METHOD_NOT_ALLOWED` (+ `Allow` header)
4. `GET /health` -> 200, needs no adapter, never throttled
5. transport-level problem -> 400 `MALFORMED_JSON`
6. body (or declared length) > 32768 -> 413 `PAYLOAD_TOO_LARGE`
7. adapter missing -> 503 `NOT_IMPLEMENTED`
8. `parse_json_body` -> 400 `MALFORMED_JSON` (empty, bad UTF-8, syntax, `NaN`, duplicate key, nesting too deep)
9. `model_validate` + `_check_request_rules` -> 422 `VALIDATION_ERROR` with field paths
10. `_call_adapter` -> 429 `THROTTLED` / 503 `ADAPTER_TIMEOUT` / adapter's own 429, 502, 503 / else 500
11. `_validated_output` -> 500 `INTERNAL_ERROR` if the adapter's shape or `mode` is wrong

Every response gets `X-Request-Id`, `X-TradeMind-Mode`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`.
Error body: `{"error": {"code", "message", "fields", "requestId"}}`, built through the generated `ErrorEnvelope`.

## Algorithm assumptions and complexity

- Routing, size and shape checks are O(body size). Parsing is bounded by the 32 KiB limit.
- The concurrency cap is a `BoundedSemaphore` of `MAX_IN_FLIGHT` slots (default 4, max 16) plus a thread pool of the same size.
  The slot is released when the adapter thread finishes, not when the request times out.
- Adapter timeout default 25 s, allowed 0.1 to 28 s.
- **Not provided in B1:** retries (adapters own them, bounded), authentication (public fictional-data demo, per the guide),
  rate limiting beyond the in-flight cap (add API Gateway throttling in infra, a later B prompt).

## Known limits and remaining actions

1. Production `default_adapters()` is empty. B2+ wires real ones. Until then a deployed `live` stack serves only `/health`.
2. Duplicate JSON keys, `NaN`/`Infinity` and extreme nesting (30000 open brackets) are rejected as 400 by our own parser hooks in
   `parse_json_body`; the standard `json` module would otherwise accept duplicates silently (last one wins).
3. MISSING_BASELINE (422), unique ids, `ownerId` references and unique service per business are **not** checked by B1.
   They need domain validation (planned in a later B prompt or by the optimizer's verifier). Today those inputs pass B1 validation.
4. A timed-out adapter thread cannot be killed; it keeps its slot until it returns. Bedrock calls need their own client timeout.
5. `Retry-After: 1` is a fixed hint, not computed.
6. The in-flight cap is per Lambda container, so total concurrency is also limited by Lambda reserved concurrency (infra, later).
7. Local server uses HTTP/1.0 close-per-request, which is fine for development only.
8. Human actions needed later: AWS account access, Bedrock model enablement and region choice, CORS origin of the real frontend.

## Judge questions with grounded answers

1. **Why does a missing adapter return 503 instead of a demo answer?** A fallback that returns plausible numbers can ship
   to production unnoticed and would be presented as real results. Here the default wiring has no adapters, 503
   `NOT_IMPLEMENTED` is tested for every route in both modes, and `_validated_output` fails with 500 if a fixture-mode adapter
   is wired into a live app (`test_fixture_adapter_in_live_mode_fails_loudly_instead_of_passing_as_real`).
2. **How do you protect a model-backed endpoint from abuse and cost?** Layers, cheapest first: 32 KiB body limit before
   parsing, schema validation before any adapter runs (invalid input never reaches Bedrock; tests assert the adapter's call
   list stays empty), an adapter timeout below API Gateway's 30 s cutoff, and a cap of `MAX_IN_FLIGHT` simultaneous adapter
   calls that returns 429. Not yet done: API Gateway throttling and Lambda reserved concurrency (infra), and budget alerts
   (warnings only, not hard caps).
3. **Why one router for Lambda and local?** So the code under test is the code that runs in the cloud: `handle_event` only
   converts the event to a `Request` and the response to a proxy dict. The tests drive the local server with real HTTP and
   `handle_event` with API Gateway v2-shaped events, but real API Gateway delivery is unverified.
4. **Why don't error messages include the offending value?** User descriptions and scenarios can be private. Pydantic's default
   messages echo input. Tests plant a marker string in bad input and assert it appears in neither the response nor the logs.
5. **What does validation not catch?** Domain rules such as a missing baseline estimate (should be 422 `MISSING_BASELINE`),
   duplicate ids and dangling `ownerId`s. B1 checks shape and types only. Those rules are listed as remaining work.
