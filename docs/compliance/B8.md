## Gaps the probe found, and what B8 does about them

I ran hostile inputs against the code as it stood before changing anything.

| Gap found | Fix | Where |
|---|---|---|
| A body of type `text/plain` or a form post was accepted. A browser can send those from any website **without** a CORS preflight, so any site could trigger a state-changing or model-calling request | `415 UNSUPPORTED_MEDIA_TYPE` unless the body is declared `application/json` (UTF-8) | `middleware.check_content_type` |
| A request from an unlisted `Origin` was processed (CORS only hid the answer from the page) | `403 ORIGIN_NOT_ALLOWED` for non-GET requests; the adapter is never called | `middleware.check_origin` |
| Control characters and Unicode direction overrides in names were accepted (log forging, terminal escapes, spoofed text) | `422` with the field path; newline and tab stay legal only inside the free-text `text` field | `middleware.find_unsafe_text`, `check_text_safety` |
| Secret-like text in any log line was written as is | Every log record is redacted and tracebacks are reduced to the exception type | `middleware.redact`, `install_log_redaction` |
| Only a global throttle existed, so one client could use all of it | Per-client token bucket with bounded memory, `429` with `Retry-After` | `middleware.ClientRateLimiter` |
| `ALLOWED_ORIGIN` was only checked for `*` | Each entry must be an exact `scheme://host[:port]`; in live mode plain http only for localhost | `middleware.validate_origin_setting`, `config.load_settings` |
| No hardening headers | CSP `default-src 'none'`, `X-Frame-Options`, `Referrer-Policy`, `Strict-Transport-Security`, `Permissions-Policy` on every response | `middleware.security_headers` |
| Budget alert only described in prose | Optional `AWS::Budgets::Budget` (off unless an amount and an e-mail are both given), plus written instructions | `infra/template.yaml: MonthlyBudget` |

## Design and tradeoffs

| Decision | Why | Tradeoff |
|---|---|---|
| Origin gate applies to POST and PUT, not to GET or OPTIONS | A browser cannot read a cross-origin GET answer without CORS headers, and preflights must still return 204 (existing tests and browsers rely on it). The risk is calls that CHANGE state or spend money | A hostile page can still make a cross-origin GET (for example `/health` or a profile read); it cannot read the answer |
| A missing `Origin` header is allowed | curl, scripts and server-to-server calls send none. Browsers always send one on cross-origin calls | `Origin` is trivially forged outside a browser. This protects browser users (CSRF-style abuse). It is **not authentication** |
| Missing `Content-Type` is tolerated, a wrong one is refused | Browsers always send a type; the dangerous case is a type that avoids preflight | A non-browser client that omits the header still works |
| Rate limit keyed on API Gateway `sourceIp`, kept in memory | No new AWS resource or cost. Bounded memory (1024 clients, least recently used evicted) | **Per container, not global.** Each warm Lambda container counts separately and a cold start resets it. The global limits are API Gateway throttles and reserved concurrency. Clients behind one NAT share a bucket. Defaults 60/min, burst 30 are enough for a full smoke run |
| Redaction wraps the logging record factory, not a logger filter | Filters on a logger do not apply to records from child loggers, and Lambda's handler is not ours. A factory covers every logger including libraries | Pattern based, best effort: it cannot recognise an unlabelled secret with no recognisable shape. The code also never logs bodies or model text, which is the stronger protection |
| Tracebacks are cut to the exception type in logs | Frames and exception messages can carry secrets | Harder debugging; the request id and type are logged so the failure can be found |
| 40-character mixed-case runs are redacted (the AWS secret key shape); hex digests are left alone | SHA-256 digests and commit ids appear in logs and must stay readable | A random 40-character mixed-case identifier would also be hidden |
| Budget is optional and account-wide | AWS Budgets cannot be scoped to a stack without cost-allocation tags; creating it needs `budgets:*` permission the deploying role may not have | Default is no budget. **A budget sends e-mail; it does not stop spending**, and billing data lags by hours |

## Data flow

Request pipeline in `backend/app.py: App._dispatch` (cheapest check first): route match, preflight, method, `/health` (never limited), then for POST and PUT `check_origin` (403) and `check_content_type` (415),
then `ClientRateLimiter.check` (429), transport errors, 32 KiB cap (413), adapter present (503), parse JSON (400), `check_text_safety` (422), Pydantic validation (422), contract rules (422), adapter with timeout and in-flight cap (429/502/503/500),
output re-validation (500 on mismatch). Every response passes through `_with_common_headers` (request id, `no-store`, `nosniff`, `security_headers`, CORS only for listed origins). Every log line passes through the redacting record factory.
Errors: `{error:{code,message,fields,requestId}}` with fixed messages; `fields` holds paths, never values; an unexpected exception is a fixed `500 INTERNAL_ERROR` with no type, frame or text.

## Algorithm assumptions and complexity

Token bucket: tokens refill at `rate/60` per second up to `burst`; a request costs 1; the wait reported is `ceil((1 - tokens) / rate)` seconds. O(1) per request, memory O(1024) clients.
Text scan: iterative depth-first walk, O(size of the 32 KiB body), no recursion so nesting cannot overflow the stack (tested at 50,000 levels). Redaction: a fixed number of regular expressions over each log line, linear in line length.
Assumed, not measured: Lambda container reuse behaviour under real traffic, and that API Gateway supplies `sourceIp` (documented for HTTP API payload format 2.0).

## Known limits and remaining actions

1. **No authentication.** The `Origin` check, content-type check and per-client limit make casual abuse harder. They do not stop a determined script, which can send any `Origin` or none and rotate addresses. Reserved concurrency, API throttles and the token cap bound the cost; a budget alert tells you.
2. The per-client limit is per container (see tradeoffs). A global per-client limit would need a shared store (for example DynamoDB or an API Gateway usage plan with API keys), which is not built.
3. Redaction is best effort and cannot recognise an unlabelled secret without a recognisable shape.
4. Clients behind one NAT share one bucket; raise `CLIENT_RATE_PER_MINUTE` if that matters.
5. HSTS and CSP are set by the API; the frontend's own headers (Amplify custom headers) are Developer 3's. Not checked here.
6. The budget covers the whole account, needs permission to create, and only sends e-mail.
7. Not tested: behaviour under real load, real API Gateway throttling responses (the gateway answers its own 429 body, not our envelope), CloudWatch contents.

## Judge questions with grounded answers

1. **CORS already exists. Why add an Origin check?** CORS only tells a browser whether the page may READ the answer. The request has already been sent and acted on. A hostile page can POST to this API with no preflight if the body type is `text/plain`.
   So the server refuses unlisted origins for POST and PUT (`403`, adapter never called) and refuses any body that is not declared JSON (`415`). Neither is authentication: a script can forge or omit `Origin`.
2. **What really limits abuse and cost?** In order: API Gateway throttle (global), Lambda reserved concurrency (global, a hard ceiling), then our per-client bucket and in-flight cap (per container), then the 32 KiB body cap and the Bedrock token cap per call. The per-client bucket is per container, not global, and says so. A budget alert only e-mails; it does not stop spending.
3. **How do you stop secrets reaching the logs?** The code never logs bodies or model text. On top of that, every log record from every logger is redacted by a wrapper on the record factory (AWS key shapes, labelled secrets, bearer tokens, private keys, e-mail addresses, long token-like strings) and tracebacks are cut to the exception type. It is pattern based, so an unlabelled secret with no recognisable shape could pass. Tests include format arguments, library loggers, exceptions and a hostile request.
4. **Why does the 500 page say nothing?** Frames, file paths and exception text can reveal code layout or secrets. The client gets a fixed message and a request id; the exception type is logged with the same id so the failure can be found.
5. **Is it deployed and verified?** See "Live verification" below for exactly what was and was not checked against AWS.
