## Design and tradeoffs

| Decision | Why | Tradeoff |
|---|---|---|
| The client invents the id (`PUT /profiles/{id}`); the server enforces strength: 32 to 128 URL-safe characters, at least 10 distinct, entropy of at least 3.0 bits, no sequential run over 5, no repetition, a short guessable-word list | The route and contract are frozen (no "create id" endpoint). A strong, unguessable id is the only access control | Strength rules cannot prove randomness. About 0.03% of random ids contain a listed word and are refused; the client generates another. **The id is not authentication**: anyone holding it can read the profile |
| DynamoDB key is SHA-256 of `"trademind-profile:" + id`, not the id | Table readers, exports and logs never contain a usable id | One more step to reason about |
| Conditional put `attribute_not_exists(pk)`: second write to an id is `409 PROFILE_EXISTS` | No overwrite, no takeover of someone else's id | No update route; a profile is write-once until it expires |
| Items expire (`expiresAt`, epoch seconds, TTL 300 to 604800 s, default 86400). `GET` treats `expiresAt <= now` as 404 itself | DynamoDB TTL deletion can lag by up to 48 hours (AWS), so the app must not rely on it | Expired items may sit in the table for up to 48 h |
| `GET` uses `ConsistentRead`; stored scenario is re-validated (digest, schema, `/confirm` rules) before return | A damaged or tampered item is never returned; a just-written item is readable | Corrupt item gives a generic `500`, with a fixed reason code in logs |
| Only fictional data: best-effort check of business names (emails, phone-like numbers, etc.) gives `422 PERSONAL_DATA_SUSPECTED` | Reduces accidental real data | **Not a guarantee** and has false positives (for example a name like "Q3 2024 2025 team") |
| Table is on-demand, TTL on, AWS-owned key encryption, no PITR, `DeletionPolicy: Delete`; created only when `EnableProfiles=true` | No capacity to size or forget; disposable demo data goes with the stack | Redeploying without `-EnableProfiles` **deletes the table and its data** (documented and printed by `deploy.ps1`) |
| IAM is a separate `AWS::IAM::Policy` with `dynamodb:PutItem` and `dynamodb:GetItem` on the one table ARN only, also conditional | Base role is unchanged when profiles are off; no scan/query/update/delete possible | None |
| AWS errors map to `429 THROTTLED` / `503 UNAVAILABLE`; messages never contain ARNs, table names or account ids; ids and contents are never logged | Safe errors | Less detail for debugging; the AWS request id is logged instead |
| Boto3 client built lazily, connect timeout 2 s, read 3 s, 2 retries | Lambda cold start and the 29 s budget; a missing region is a clean `503` | Not tuned under load |

Rejected: overwrite/ownership model, listing or delete routes, a server-generated id endpoint (contract is frozen), a customer KMS key, point-in-time recovery.

## Data flow

`PUT /profiles/{id}` : B1 router (size cap, JSON, schema, rules) to `ProfileStore.put`: id strength, `/confirm` rules, personal-data guard, canonical JSON plus digest,
`PutItem` with condition. `GET /profiles/{id}` : router to `ProfileStore.get`: id strength, `GetItem` (consistent), expiry, digest, schema, `/confirm` rules, response.
Item fields: `pk`, `scenario` (canonical JSON string), `digest`, `schemaVersion`, `purpose` ("fictional-demo"), `createdAt`, `expiresAt`.

## Judge questions with grounded answers

1. **If profile ids are client-chosen, how is data protected?** The id is the only secret, so the server refuses weak ids (length, character variety, entropy, sequences, repetition, common words) and stores only a SHA-256 hash of it.
   There is no listing route, so ids cannot be discovered. It is a capability token, not authentication, and the data is fictional by policy. It has not been tested against real DynamoDB.
2. **What stops one user overwriting another's profile?** The write is a conditional put (`attribute_not_exists`), so an existing id returns `409`; the IAM policy has no update or delete action. Tested against a double that imitates the condition; real-table behaviour is NOT RUN.
3. **What if DynamoDB TTL is late?** AWS documents deletion can lag up to 48 hours. `GET` checks `expiresAt` itself, so expired data is never returned. The item may still exist in the table for that time.
4. **Why is this off by default?** It adds a billable resource and stored data. With `EnableProfiles=false` the template creates no table or policy and the routes return `503 PERSISTENCE_DISABLED`; the core workflow does not use them.
5. **Is this verified in AWS?** No. Template lint, build and 103 local tests pass. Deployment, IAM, TTL and latency are UNVERIFIED until a human runs the steps in `docs/deployment.md` section 5a.
