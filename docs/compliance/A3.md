## Design explanation

### New module: `optimizer/feasibility.py`

A3 adds a dedicated feasibility module with two public functions:

**`validate_assignment(scenario, assignments) → list[AssignmentViolation]`**

Validates a fully specified assignment list after-the-fact. Returns all violations (never raises). Checks run independently so every problem is reported in one call:

1. Unknown deliverable/provider IDs
2. Coverage — missing or duplicate assignments per deliverable
3. Service compatibility — provider must have an estimate for the service
4. Duration — `assignment.minutes` must equal the provider's estimate exactly; invented durations are rejected
5. Capacity — `effortMinutes ≤ capacityMinutes` per business (includes coordination charge when applicable)
6. No-worse-off — `netSavingsMinutes = baseline - effort ≥ 0` per business

Steps 5–6 only run when coverage is complete and all IDs/services are valid — partial input can't produce meaningful capacity/savings checks.

**`explain_infeasibility(scenario) → InfeasibilityReport`**

Analyses a scenario by checking each business's self-assignment (no cross-business work, no coordination charge). If self-assignment fails for any business, the scenario is globally infeasible.

Reports three independent categories:
- `capacity_violations` — businesses where self-production exceeds capacity
- `savings_violations` — businesses where self-production yields negative net savings (cannot occur in pure self-assignment since effort = baseline, but included for completeness and future use)
- `unsupported_services` — deliverables whose owner has no estimate (MISSING_BASELINE territory)

**Important:** this is observed constraint analysis, NOT a minimal unsatisfiable core (MUC/IIS). The function explicitly does not claim to find a MUC.

### Integration with engine.py

The INFEASIBLE branch of `solve()` now calls `explain_infeasibility()` via a lazy import (to avoid circular dependencies) and includes the report's `summary()` string in the `reasons` list. This means INFEASIBLE results carry truthful diagnostic text like "Infeasibility observed: capacity exceeded for: devco".

### Circular import management

`engine.py` → (lazy) `feasibility.py` → `errors.py` ← `engine.py` (indirectly)

The lazy import (`from optimizer.feasibility import explain_infeasibility` inside the function body) breaks the potential circular import. This is the standard Python pattern for this case.

## Algorithm assumptions

1. `validate_assignment` assumes the scenario has already passed Pydantic validation (`extra=forbid`, confirmed=True).
2. `explain_infeasibility` analyses self-assignment only. It does NOT enumerate all possible allocations — that would duplicate the solver.
3. "Duration must match provider's estimate exactly" — the contract forbids invented or interpolated durations.
4. Coordination is charged in `validate_assignment` using the same logic as the solver: a business is "involved" if it provides work it doesn't own OR any of its deliverables is done by someone else.
5. `savings_violations` from self-assignment analysis is always empty (since `effort = production = baseline` in pure self-assignment with no coordination). The field is retained for future simulation use cases where partial changes might produce negative savings even in self-assignment.

## Judge questions

**Q1: Why does `validate_assignment` return violations rather than raising an exception?**  
A: Raising on first error would hide subsequent problems. By collecting all violations, the backend can return a single 422 response with a complete `fields` list — the user (or frontend) sees every issue at once. This follows the contract's `{error:{code,message,fields:[...]}}` envelope, which expects multiple field references.

**Q2: What is the difference between `MISSING_BASELINE` and `INCOMPATIBLE_SERVICE`?**  
A: `MISSING_BASELINE` means the *owner* of a deliverable has no estimate for the required service — this is invalid input that blocks the solver entirely (→ 422 before enumeration). `INCOMPATIBLE_SERVICE` in `validate_assignment` means a *non-owner provider* was assigned to a deliverable for which it has no estimate — this is a constraint violation in a supplied assignment list. The solver never produces such assignments; this check protects against tampered client-supplied results.

**Q3: Does `explain_infeasibility` compute a minimal unsatisfiable core?**  
A: No. It reports observed constraint violations based on self-assignment analysis. It may report redundant constraints — for example, both capacity and savings violations for the same business (since `effort > capacity` implies `effort > baseline` when `baseline ≤ capacity`). A true MUC algorithm would require additional search; this function provides truthful diagnostics without that claim.
