## The optimizer interface this code assumes (CONFIRM WITH DEVELOPER 1)

```python
# optimizer/api.py
def optimize(scenario: dict) -> dict | Result    # JSON in, contract `Result` out
```
Pure and deterministic; no I/O; does not mutate its input; raises `NotImplementedError` if unfinished. If Developer 1's real signature differs,
the only file to change is `backend/optimization.py` (`load_optimizer_function` / `run_optimizer`). The prompt names `optimizer.api.optimize` but not its signature, so this is an
assumption, not a fact. If `optimizer.api` exists but fails to import, `/optimize` answers 503 `OPTIMIZER_UNAVAILABLE`. If it is absent, 503 `NOT_IMPLEMENTED`.

## Design: how /explain stays grounded

| Step | What happens | If it fails |
|---|---|---|
| 1 | Scenario validated (`validate_scenario`, B3), before anything else | 422 (`MISSING_BASELINE` etc.). Optimizer and Bedrock not called |
| 2 | The optimizer is **run again** on the supplied scenario. Client math is never trusted | 500 if the optimizer misbehaves |
| 3 | The recomputed result must **equal** the supplied one in every field including the certificate | **422 `RESULT_MISMATCH`** with differing *paths* (never values). **Bedrock not called** |
| 4 | Facts are built from the **recomputed** result only, with durations pre-formatted ("3 hours", "62.5") | |
| 5 | One Bedrock call, temperature 0. System prompt: copy numbers, never calculate, no money, no promises. Names go in as escaped JSON data | Same error mapping as B2 (429 / 502 / 503) |
| 6 | The text is checked: every quantity with a unit (minutes, hours, %) must be one we supplied, no currency, length bounded | **502 `MODEL_UNGROUNDED_OUTPUT`**. Text withheld, no retry |

The response is only `{text, mode}`. There is no code path by which an explanation can change a number, the result or the certificate, and on
any failure no explanation is returned. There is no canned fallback text, because that would be simulated output presented as real.

## Tradeoffs

| Decision | Why | Cost |
|---|---|---|
| Re-run the optimizer in `/explain` instead of verifying the client's numbers by formula | The contract says "recompute result ... never trust client math". Equality with a fresh run also covers the certificate and reasons | Doubles optimizer work on `/explain` (cheap: at most 729 combinations) |
| Check the optimizer's arithmetic in the backend | Defense in depth: a solver bug cannot reach a user as a confident wrong number | The checks encode the contract's definitions; if the contract changes, two places change (tested by cross-validation against the stand-in) |
| The checks do not prove optimality | Re-solving in the backend would duplicate Developer 1's work | A solver that returns a valid but suboptimal allocation passes. That is the optimizer's own test suite's job |
| `/optimize` wired in fixture mode too | Developers 3 and 1 can use it locally. The computation is real; only `mode` echoes the app mode | A fixture-mode `mode` label sits on a real computation. Documented |
| Grounding check on units, not on all prose | Deterministic and cheap; blocks the failures that matter (invented figures, money) | Cannot catch wrong reasoning, a misspelled name, or a bare number such as "three businesses" |
| No automatic repair on ungrounded text | Simplicity and bounded cost: at most one model call per request | A user may need to press the button again |
| Business names excluded from the allowed-number set | A name like "Agency 77 hours" must not let the model quote 77 | Names with numbers in them are never treated as evidence |

## Judge questions with grounded answers

1. **How do you know the explanation isn't making numbers up?** Three layers. The server recomputes the result and refuses a mismatched one before calling the model. The model is given pre-formatted facts and told to copy, not calculate. Then code checks every number with a unit in the reply against the facts we sent, and rejects currency; anything else is withheld with a 502. Removing each layer breaks a test (13-way mutation check).
2. **What if a client edits the result before asking for an explanation?** It gets 422 `RESULT_MISMATCH` naming the changed fields, and Bedrock is never called (9 tamper cases tested, including a forged certificate digest). The explanation is also built from the server's recomputation, not the client's object (tested by object identity).
3. **What stops a buggy optimizer from showing a wrong number?** `result_problems` recomputes the contract's identities from the scenario (baseline, production, coordination once per exchanging business, effort, net savings, capacity, no one worse off, totals, status). A violation returns a generic 500, never the numbers. It cannot prove optimality, which is the optimizer's own job.
4. **Is this tested against the real optimizer?** No, not yet. The optimizer isn't merged, so every `/optimize` test uses an independent brute-force stand-in that reproduces the guide's figures (1440, 540, 900; 720 with coordination 60; `no_exchange`; `infeasible`) by computation. The real-optimizer test is in the suite and is skipped, labelled NOT RUN, until the merge.
5. **What happens in production if the optimizer is missing or broken?** `/optimize` and `/explain` answer 503 (`NOT_IMPLEMENTED` or `OPTIMIZER_UNAVAILABLE`). Production wiring never builds a stand-in; only tests do.
