## Design explanation

### New module: `optimizer/certificate.py`

A5 adds `generate_certificate` and `verify_certificate` that are **completely independent** from the solver path — they share no code with `engine.py`, `metrics.py`, or the solver's internal `_build_certificate`. They reimplement the same accounting formulas from the frozen spec from scratch. This independence is the whole point: a verification that shares code with the thing it's verifying is not independent.

**`generate_certificate(scenario, assignments) → Certificate`**

1. Runs `_run_checks()` from scratch.
2. Raises `ValueError` with check names if any check fails.
3. Only on full pass: computes SHA-256 digests and returns a `Certificate`.

**`verify_certificate(scenario, assignments, certificate) → VerificationResult`**

1. Runs `_run_checks()` independently.
2. Recomputes both digests from the supplied scenario and assignments.
3. Compares recomputed digests against the certificate's stored digests.
4. Returns `VerificationResult(valid=True)` only when all checks pass AND both digests match.

**`_run_checks(scenario, assignments) → list[_CheckResult]`**

Nine independent checks:
1. `coverage_complete` — exactly one assignment per deliverable, no extras, no duplicates
2. `all_ids_known` — every deliverableId and providerId exists in the scenario
3. `service_compatibility` — provider has an estimate for the deliverable's service
4. `duration_matches_estimate` — `assignment.minutes` equals provider's estimate exactly
5. `baselines_computable` — no missing owner estimates
6. `capacity_respected` — `effort ≤ capacity` for every business
7. `no_worse_off` — `netSavings ≥ 0` for every business
8. `totals_consistent` — cross-verification: `total_effort = total_production + total_coordination`
9. `integer_arithmetic` — all totals are Python `int` (no floats)

Checks 6–9 are skipped with a "skipped" reason if earlier checks fail (can't compute effort without clean coverage/IDs/service).

### What the certificate proves and does not prove

**Proves:**
- Coverage, service compatibility, duration, capacity and no-worse-off constraints are satisfied.
- The arithmetic (baseline, production, coordination, effort, netSavings) is correct.
- SHA-256 digests match the canonical serialisation of the scenario and assignment list.

**Does NOT prove:**
- Cryptographic identity of any party.
- Legal enforceability of any business arrangement.
- Equal service quality across providers (stated assumption, not verified).
- Commercial profit or monetary benefit.
- That the assignment is globally optimal.
- Honesty of supplied estimates.

These limitations are stated explicitly in `certificate.assumptions` so they appear in every generated certificate.

### Canonical JSON and display rounding

Canonical serialisation: keys recursively sorted, arrays preserve order, no whitespace, UTF-8. This is deterministic across platforms and Python versions.

Display conversions (e.g. 480 minutes → 8 hours) must not alter the source integer values used for hashing. The certificate hashes the integer-minute representation. Any display layer that converts to hours must convert back to integer minutes before any feasibility or digest operation.

## Judge questions

**Q1: What does the SHA-256 digest actually detect?**  
A: It detects any change to the scenario or assignment list after the certificate was issued. If a scenario field is modified (e.g., a capacity changed), or if an assignment's provider or minutes is altered, the recomputed digest will differ from the stored one and `verify_certificate` will return `valid=False`. It does not detect scenarios where someone replaces both the certificate AND the input — but that is outside the threat model for a hackathon demo. It is not a cryptographic signature.

**Q2: Why is `verify_certificate` independent from the solver?**  
A: If verification calls the same code that generated the certificate, it cannot catch bugs in that code — it would reproduce the same errors. By reimplementing all checks from the frozen spec in `_run_checks()`, we get genuine independent verification. Any discrepancy between the solver's output and the specification will show as a failed check.

**Q3: Why does `generate_certificate` raise rather than return a partial certificate?**  
A: A certificate that failed some checks would be meaningless at best and misleading at worst. The contract states `verification: "valid"` as the only possible value — so a certificate either certifies a valid result or does not exist. Raising on failure forces the caller to fix the problem before a certificate can be issued.
