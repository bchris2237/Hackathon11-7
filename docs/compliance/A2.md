## Design explanation

### What A2 adds to A1

A1 implemented the full engine in `optimizer/engine.py`. A2 formalises the public API surface:

1. **`enumerate_assignments(scenario)`** — exposed explicitly as a public function on `solver.py` and `engine.py`. Returns every candidate assignment map `{deliverableId: providerId}` in deterministic order without any feasibility filtering. This is the raw search space the solver iterates over.

2. **`optimize(scenario)`** — a stable alias for `solve()` on `solver.py`. The backend (Developer 2, B4) imports `optimize` as the preferred name for the `/optimize` route handler. Both names are stable.

3. **Bound guard in `enumerate_assignments`** — raises `ValueError` before enumeration if `len(businesses) > 5` or `len(deliverables) > 6`. Pydantic already rejects these at parse time; the engine guard makes the algorithmic bound explicit and testable independently.

4. **Brute-force oracle in `test_solver.py`** — an independently coded reference implementation that replicates the algorithm from scratch (no shared code with `engine.py`) and cross-checks solver output on the canonical and coordination fixtures.

### Algorithm complexity

| Step | Complexity |
|---|---|
| Baseline validation | O(B + D) |
| Provider list construction | O(D × B) |
| Enumeration | O(P^D) where P ≤ 5, D ≤ 6 → at most 15 625 iterations |
| Per-candidate evaluation | O(D + B) |
| Total | O(15 625 × (D + B)) — effectively O(1) at the supported scale |

### Tiebreak (integer arithmetic only)

1. Minimize `sum(effortMinutes)` — total effort across all businesses.
2. Minimize `max(effortMinutes_i × total_baseline)` — integer proxy for max effort/baseline ratio; avoids division.  
   `baseline_i = 0` → ratio proxy = 10^15 (infinity sentinel).
3. Lexicographic `sorted([(deliverableId, providerId), ...])`.

No floats appear anywhere in the solver path.

## Input / output / error data flow

```
POST /optimize (B4 backend)
  → OptimizeRequest.scenario (Pydantic validated, extra=forbid)
  → optimizer.solver.optimize(scenario)
      → optimizer.engine.enumerate_assignments(scenario)   [A2 — bound guard]
          → _build_feasible_providers()
          → itertools.product(*provider_lists)
          → list[dict[str,str]]
      → for each candidate: _evaluate_candidate()
          → production, involvement, effort, feasibility gates
      → if collaboration found: _build_certificate()   [SHA-256]
      → Result(status, assignments, businessMetrics, totals, certificate)
  → OptimizeResponse(result, mode)
  → HTTP 200

Errors:
  MissingBaselineError  → caught by backend → 422 MISSING_BASELINE
  ValueError (bound)    → caught by backend → 422 VALIDATION_ERROR
```

## Algorithm assumptions

1. All estimates are positive integers (enforced by schema `ge=1`).
2. Capacity and coordination are non-negative integers (`ge=0`).
3. Every owner has an estimate for each of its own deliverables' services (enforced pre-flight).
4. Service quality is assumed equal across providers (stated in certificate assumptions).
5. Coordination is charged at most once per business per scenario, regardless of how many cross-business assignments it participates in.
6. "No worse off" means `netSavingsMinutes ≥ 0` for every business — not just globally.

## Judge questions

**Q1: Why 5^6 = 15 625 and not something larger?**  
A: The MVP supports at most 5 businesses and 6 deliverables. Each deliverable can be assigned to at most 5 providers (all businesses). In the worst case that gives 5^6 = 15 625 candidates. Exhaustive enumeration over this space runs in microseconds and guarantees we never miss the optimum. We explicitly state this is not a scalable algorithm — larger networks would require a redesigned bounded solver.

**Q2: How does `enumerate_assignments` guarantee determinism across different runs and machines?**  
A: Deliverables are sorted lexicographically by ID before building the candidate lists. Within each deliverable, the owner always comes first; other providers are sorted lexicographically. The Cartesian product is generated in this fixed order, so the same scenario always produces the same sequence of candidates regardless of Python dict insertion order or business list order in the input.

**Q3: Why is `optimize()` a separate function from `solve()`?**  
A: The backend (Developer 2) imports `optimize` as the stable name for the `/optimize` route. Having both names means the backend doesn't need to change if internal naming evolves, and existing tests that call `solve()` keep working without modification. Both delegate to the same `engine.solve()` implementation — there is no duplication of logic.
