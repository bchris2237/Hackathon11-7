## Data flow

Error: `ApiClient.request` classifies the failure at the source (timeout vs network vs HTTP vs envelope, with `Retry-After` from the response header). The component keeps the raw error in its status. `AsyncError` calls `classifyError` and renders: a headline, the earlier sentence unchanged (prefix + message with code and request id + "Your inputs are unchanged." style suffix), a hint, the server's wait if any, and a Try again button only if `retryable`. Local messages (plain strings) get the same box without a headline or retry.

Retry rules: validation (422), malformed (400), mode mismatch and contract mismatch offer no retry because repeating the same request cannot help. Timeout, disconnect, 429, 502 and 503 offer a retry that the user must click. While the server's `Retry-After` runs, the button is disabled and counts down. A timeout hint says the request may still have been processed.

Automatic retry: only `health()`. Transient failures are retried up to `healthRetries` (2); the wait is the server's Retry-After if given and at most `maxRetryWaitMs` (5 s), otherwise doubling backoff from 250 ms. A longer Retry-After stops the loop so the user sees the number. Aborting stops the wait.

Double submit: `useLatestRequest().start()` refuses while one request runs; `invalidate()` (edit, cancel, mode switch, unmount) aborts it and makes its late reply recognisable as stale; `done()` in `finally` frees the slot only for the request that still owns it. Buttons are also disabled while pending.

Mode switch: `switchMode` dispatches `reset_derived` (bumps the version and clears confirmation, result, what-if) and changes the mode, which creates a new `ApiClient`. Components reset on the new client, and the health check is repeated. Nothing is silently swapped: the banner changes immediately, and if the backend still runs in the other mode the existing mode-mismatch alert appears and its results are discarded.

## Assumptions and limits

- The switch changes what the app accepts; it does not reconfigure the backend. With one backend, the other mode shows a mismatch, by design.
- The switch is available in every build. It is explicit and clearly labelled, but a deployment that should never offer fixture mode would need a build-time guard, which needs a joint decision because only two `VITE_` variables are allowed.
- Headline and hint wording was not user-tested. Layout was not inspected by eye.
- `Retry-After` is only read from the header; the error envelope has no field for it.
- Rate-limit counting is the server's job; the client does not throttle itself beyond one request at a time per screen.
- Complexity: constant work per request; the countdown ticks every 250 ms while visible.

## Judge questions

1. Why only retry `/health` automatically? It is a read with no side effects. The other calls cost model time or change what the user is approving, so repeating them is the user's decision, and a timeout may have succeeded on the server.
2. What does Retry-After do here? If the server sends it, the retry button stays disabled and counts down, and the health loop will not wait longer than 5 s on its own. If the browser cannot read the header (CORS), we say nothing about a wait and allow a manual retry; the browser test shows that case.
3. Does the fixture switch hide failures? No. It clears everything produced under the other mode, changes the banner at once, and any answer labelled with the wrong mode is discarded with an alert.
4. How is a double click handled? The button disables on the next render and `start()` refuses a second request while one is running, so one request goes out (tested with a double click).

## Update after C7: the switch is no longer a banner button

The first version put "Switch to live mode / fixture mode" in the banner. That let a user click the app into a mode the backend did not run, which produced the mode-mismatch alert and a dead end (seen in practice). Now:
- The banner has no button. The only switch is the button inside the mismatch alert, and it always offers the mode the backend reported (`Switch the app to fixture mode`), so a click resolves the mismatch instead of causing one.
- A "Check the backend again" button sits under the health line, so after restarting the backend in another mode the page can re-read `/health` without a reload. The alert tells the user both options: switch the app, or restart the backend with `APP_MODE=...` and check again.
- Everything else is unchanged: switching clears confirmation, result, what-if and extraction preview, keeps typed inputs, and the mode badge stays visible. There is still no automatic or silent switch.
- Tests: the mode-switch tests in `Resilience.test.tsx` and `resilience.spec.ts` were rewritten for this (including: no switch control exists while the app and backend agree).
