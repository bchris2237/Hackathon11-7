## Design explanation

A7 adds Hypothesis property-based tests in `tests/optimizer/test_properties.py`. This is additive fuzz/regression coverage — it does not replace the deterministic contract tests in `test_contract.py`, `test_solver.py`, `test_feasibility.py`, `test_metrics.py`, `test_certificate.py`, or `test_simulation.py`. The entire file can be skipped without affecting the critical demo.

### Scenario generator (`valid_scenarios`)

A Hypothesis `@st.composite` strategy that generates small, valid 3-business scenarios:
- Random deliverables (1–3), each owned by a random business with a random service.
- Each business is guaranteed to support the services its own deliverables require (so `MISSING_BASELINE` never fires — that path is tested separately in `test_contract.py`).
- Bounded numbers (minutes 30–300, capacity 0–900, coordination 0–200) keep the space small enough for the exhaustive oracle to run on every example.

### Independent brute-force oracle (`_oracle_best`)

Coded from scratch inside the test file — no shared code with `engine.py`. It independently enumerates all assignments and returns the expected status and optimal total effort. The solver's output is cross-checked against it.

### Determinism / recorded seed

`settings(derandomize=True)` makes the suite reproducible run-to-run. Hypothesis's `.hypothesis` database preserves minimal failing examples automatically, so any regression produces the same minimal counterexample.

### Property groups

| Class | Properties asserted |
|---|---|
| `TestSolverInvariants` | coverage, provider-service-support, duration-equals-estimate, capacity, no-worse-off, totals sum consistency, effort = production + coordination, collaboration requires cross + positive savings, infeasible/no_exchange emptiness, integer minutes |
| `TestOracleAgreement` | solver status matches oracle; optimal effort matches oracle |
| `TestCertificateProperty` | collaboration certificate verifies; tampered minutes fail verify() |
| `TestMonotonicFeasibility` | raising all capacities never makes a feasible scenario infeasible; never reduces optimal total savings when both are collaboration |
| `TestDeterminism` | repeated optimize() is identical |

Note on monotonicity: we assert the **feasible set** does not shrink and total savings does not drop — we deliberately do NOT assert that every individual business's saving increases, because that is not guaranteed by the model (the optimum may shift to a different allocation).

## Algorithm assumptions and complexity

- Each generated scenario is small (≤3 businesses, ≤3 deliverables) so the oracle's exhaustive search is cheap.
- `max_examples=150` per property keeps total runtime near 1 second.
- `derandomize=True` means the same examples are generated each run — deterministic CI.

## Judge questions

**Q1: How do property tests add confidence beyond the fixed-fixture tests?**  
A: Fixed fixtures test specific known cases. Property tests generate 150 random valid scenarios per property and assert invariants hold for all of them — covering combinations no human wrote by hand. Each scenario is also cross-checked against an independently coded brute-force oracle, so any divergence between the production solver and the specification is caught automatically.

**Q2: Why don't you assert that raising capacity increases every business's savings?**  
A: Because it isn't true in general. Raising capacity can expand the feasible set and shift the optimal allocation to a different arrangement. The correct monotonicity claim is weaker: the feasible set never shrinks, and the optimal *total* net savings never decreases (the old optimum remains feasible). We assert exactly those two properties and nothing stronger.

**Q3: How are failures reproduced?**  
A: `settings(derandomize=True)` fixes the example generation, and Hypothesis's local `.hypothesis` database stores the minimal failing example. A failing property produces the same minimal counterexample on every run, which is then added as a deterministic regression test.
