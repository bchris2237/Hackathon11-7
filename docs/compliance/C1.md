## Data flow

Input: `readConfig()` reads `VITE_API_BASE_URL` and `VITE_DATA_MODE` (config.ts, unchanged). `App` builds one `ApiClient`. On mount it calls `client.health({signal})`; the effect cleanup aborts so late responses cannot overwrite state.

Output: banner (mode), health panel (`Backend OK` with mode/commit).

Errors: network failure or timeout -> `ApiUnavailableError`; v1 envelope -> `ApiError` (code, fields, requestId shown); non-JSON/non-contract -> `ApiUnavailableError`; response `mode` differing from configured mode -> `ModeMismatchError` and the result is discarded. A caller abort is rethrown as `AbortError` and not displayed. Nothing is ever replaced by sample data: fixture mode is the same HTTP path, and it only means the backend itself reports `mode: "fixture"`.

## Assumptions, limits

- Fixture mode relies on the backend labelling its own responses; the frontend does not fake solver output.
- Default timeout 15 s per call (`DEFAULT_TIMEOUT_MS`), configurable per client.
- `confirm` has no `mode` field in the contract, so no mode check applies there.
- Layout was not inspected in a real browser at desktop or mobile widths. Responsiveness rests on Tailwind classes only.
- Contrast and screen-reader behavior are not formally audited.

## Judge questions

1. How do you prevent a live failure from looking like a success? The client has one HTTP path, throws typed errors, and the UI renders them; there is no fixture import in the live path. Covered by "never falls back" and the live-mode App test.
2. What if the backend runs in a different mode than the frontend expects? Optimizing/extracting responses with a mismatched `mode` throw `ModeMismatchError`, and `/health` mismatch shows an alert.
3. Why abort and timeouts? Stale responses must not overwrite newer state, and a hung Lambda must give a readable message instead of a spinner.
