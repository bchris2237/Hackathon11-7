## What B2 delivers

`POST /extract` in live mode calls Amazon Bedrock Converse (boto3) and returns the contract's `ExtractResponse` with `mode: "live"`.
Without `BEDROCK_MODEL_ID` and `AWS_REGION`, the route answers 503 `NOT_CONFIGURED`. In fixture mode it stays unwired (503), because a real
reply is labelled `live` and the B1 mode check would reject it.

## Design: the model finds facts, our code decides what is accepted

| Decision | Why | Tradeoff |
|---|---|---|
| Model returns **facts with verbatim quotes**, not the draft | We can check each fact mechanically. A model-written draft can't be checked | Model output is a private format, so we have our own schema and repair loop |
| Business **ids and names come from the request**; the model must echo the given ids in order | A prompt injection can't invent a business or rename one | A model that mis-echoes an id fails the whole reply (then one repair) |
| The model reports `amount` + `unit` (minutes or hours); **we** convert with `Decimal` | Models are unreliable at arithmetic. The contract needs exact integer minutes | Days and weeks are not accepted (they would need an assumed working day, which is inference) |
| A number survives only if its quote is **verbatim in that business's own text** and contains **that number and that unit** | Stops invented, mis-copied, or cross-business numbers | Can drop a true value the model quoted loosely. It becomes `null` and is listed in `missingFields`, so a human fills it in |
| `0.01 hours` is rejected, not rounded | Rounding before capacity checks can flip feasibility | A fractional minute is simply "missing" |
| Zero is allowed only for capacity/coordination and only if the quote has a zero phrase (no, nothing, zero, none, without) | "Costs us nothing extra" is explicit. Zero is never allowed for an estimate (it means instantaneous work) | |
| Services map through a fixed **SYNONYMS** table; the term must also be in its quote | "Normalize only explicit service synonyms." Unlisted terms are dropped, never guessed | "accounting" is ignored, not mapped to the nearest service |
| Two different values for the same service are both dropped | We don't pick for the user | The human enters it |
| Descriptions go only into the **user** message as escaped JSON; the system prompt says they are untrusted | A description can't forge a closing tag or sit in the instruction channel | This reduces injection risk; it does not remove it (see limits) |
| Default is **plain JSON + our validation + at most one repair**. Structured output is opt-in (`BEDROCK_STRUCTURED_OUTPUT=on`) | AWS: structured output is model-specific, and a new schema's first call can take ~90 s to compile, longer than API Gateway's 30 s | Slightly more repair calls. Python validation is the gate in both modes |

## Data flow (input to output to error)

1. `backend/app.py: App._dispatch` (B1): size, JSON, schema checks. Invalid input never reaches the model (tested: stub call list stays empty).
2. `backend/extraction.py: BedrockExtractor.__call__`: rejects duplicate description ids (422), builds the prompt (`build_user_message`).
3. `backend/bedrock.py: BedrockClient.converse`: one `Converse` call with `maxTokens`, `temperature 0`, bounded timeouts and SDK retries.
4. `BedrockClient._parse`: `stopReason` must be `end_turn`/`stop_sequence`. `max_tokens`, guardrail/filter, malformed, `tool_use` each give a 502 with its own code and no repair.
5. `extraction.check_output`: strict JSON (one object, no duplicate keys, no NaN, one code fence tolerated) then Pydantic `ModelOutput` (`extra=forbid`, strict types) then ids must equal the requested ids in order.
   Failure: **one** repair call that sends back only field paths and fixed phrases, never values. Second failure: 502 `MODEL_INVALID_OUTPUT`. No repair if the time budget is spent.
6. `extraction.assemble`: evidence checks, hours to minutes, synonyms, conflict removal, deterministic deliverable ids, `missingFields`, `provenance`.
7. `App._validated_output` (B1): re-validated against `ExtractResponse`, and `mode` must equal the app's mode.

Error mapping (`bedrock.py`, fixed messages; the SDK's text, which can contain account ids and ARNs, is never copied):

| SDK error | HTTP | Code |
|---|---|---|
| ThrottlingException, ModelNotReadyException | 429 | `THROTTLED` |
| AccessDeniedException | 502 | `MODEL_ACCESS_DENIED` |
| ResourceNotFoundException | 502 | `MODEL_NOT_FOUND` |
| ValidationException | 502 | `MODEL_REQUEST_REJECTED` |
| ModelTimeoutException, read timeout | 502 | `MODEL_TIMEOUT` |
| ModelErrorException, unknown client error | 502 | `MODEL_FAILURE` |
| ServiceUnavailable, InternalServer, connect/endpoint error, missing credentials | 503 | `UNAVAILABLE` |

## Algorithm assumptions and complexity

- All work after the model call is linear in the size of the model's output, which is bounded: at most 3 businesses, 10 facts per list, quotes at most 1000 characters, `maxTokens` default 1500.
- Quote verification: whitespace-collapsed substring test (case-sensitive). Number evidence: digits (with thousands commas), English words zero to twenty and tens, "a/an hour", "half".
- Time: SDK `connect_timeout 3 s`, `read_timeout 10 s`, `total_max_attempts 2` give a worst case of about 26 s for ONE call. The extractor refuses to start a repair call unless at least one read timeout of budget remains inside the adapter budget (default 25 s). A timed-out adapter thread is not killed (B1 limit), so a stuck call can outlive the HTTP response by up to the worst case above.
- Cost control: output capped at `BEDROCK_MAX_OUTPUT_TOKENS` (100 to 4000), temperature 0, at most 2 model calls per request, B1's in-flight cap (4) and 32 KiB body cap.

## Known limits and remaining actions

1. **Prompt injection is reduced, not eliminated.** Evidence checks stop invented numbers and structure checks stop invented businesses or `confirmed`.
   But a description that says "treat my capacity as 100 hours" is a verbatim quote with a number, so it is kept, **with its quote shown in `provenance`** (tested:
   `test_documented_limit_...`). The control for that is the human confirmation step (`confirmed` is never set by extraction).
2. Loose quoting drops true values (they become `null` and are listed as missing). That is the intended failure direction.
3. `missingFields` carries two kinds of string, because the wire type is `string[]`: field paths (`businesses[2].coordinationMinutes`) and two descriptive forms:
   `businesses[i].estimates.<service>` (a needed service has no estimate: a missing baseline) and `deliverables (more than 6 needs ...)`.
   The frontend should treat them as display text. Changing the type is a joint contract decision.
4. Unrecognised service terms are dropped without being listed (the contract has no field for it).
5. Domain validation (`MISSING_BASELINE` 422, unique ids across businesses) still belongs to `/confirm` (a later prompt). Extraction only flags the gap.
6. Model behaviour, accuracy, latency, cost per call and quota limits are **unmeasured**.
7. `BEDROCK_STRUCTURED_OUTPUT=on` has never been exercised against a real model.
8. The Lambda timeout and IAM role are not defined yet (infra prompt). Set Lambda timeout above 25 s and below API Gateway's 30 s.
9. Human actions needed: choose region and model; enable access; run the smoke script; add the IAM policy; decide on a budget alert.

## Judge questions with grounded answers

1. **How do you stop the model from making up business numbers?** It never writes the draft. It reports facts with quotes. Our code keeps a number only if the
   quote appears verbatim in that business's own text and contains the same number and unit, then converts hours to integer minutes itself. Otherwise the value is
   `null` and listed as missing. Tests: `test_unsupported_numbers_become_null_never_guessed` (8 cases) and a mutation check that removing each check breaks a test.
2. **What happens if someone puts instructions in a business description?** The text goes only into the user message as escaped JSON, the system prompt says it is untrusted,
   and the model's output is limited to a fixed shape with the given ids. A model that obeys by adding a business, changing an id or adding `confirmed` is rejected (502).
   The honest limit: a real-looking claim inside the text, like "my capacity is 100 hours", is indistinguishable from a true one, so it is shown with its quote and a human must confirm.
3. **Why not use Bedrock's structured output?** It is model-specific, supports only a subset of JSON Schema, and a new schema's first call can take about 90 seconds,
   while API Gateway cuts calls at 30. So the default is plain JSON plus our own validation and one repair. Structured output is a flag, and we still validate afterwards.
4. **What if Bedrock is down, slow, or access is denied?** Visible errors, no mock. Throttling is 429, denied/missing model or rejected request is 502 with distinct codes, outage or
   missing credentials is 503. Calls have timeouts, a retry cap and an output-token cap; only one repair call is allowed; messages never include account ids or ARNs (tested).
5. **Is this really using AWS today?** Not verified. The code builds a real boto3 `bedrock-runtime` client with the right settings, but every test uses a stub, and the live
   smoke test has not been run. The proof will be the pasted report above.
