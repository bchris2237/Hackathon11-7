## Design and tradeoffs

| Decision | Why | Tradeoff |
|---|---|---|
| `deploy.ps1` stops after the build unless `-Deploy`, shows the account and region, and requires typing the account id; `sam deploy` then shows the change set | An AWS deployment is billable and hard to undo, and the shell/IDE may hold credentials for an account you did not mean | One extra prompt. `-Yes` exists for automation |
| Region is never defaulted (`-Region` required); `AWS_REGION` is not set in the template | Lambda reserves `AWS_REGION` (AWS docs) and always provides its own region, so Bedrock is called in the stack's region | The stack must be deployed in a region where model access is enabled |
| Model id, resource ARNs and origin have **no defaults** and reject wildcards by pattern | The project never guesses a model or an origin; least privilege | The operator must look up three values |
| IAM: `bedrock:InvokeModel` only, on exactly the ARNs given; logs only to the function's own log group; no managed policies | Converse requires `bedrock:InvokeModel` (AWS Converse reference); an inference profile also needs the foundation-model ARN of each region it routes to (AWS "Prerequisites for inference profiles") | Getting the ARN list right is on the operator; the guide and troubleshooting table cover the common mistake |
| **No** `CorsConfiguration` on the HTTP API | The Lambda (B1) is the single CORS authority; two layers could disagree and API Gateway would answer preflights itself | The catch-all routes (`ANY /{proxy+}`, `ANY /`) send every method, including OPTIONS, to Lambda |
| `$default`-style catch-all routing so unknown paths still get **our** error envelope | The UI parses one error shape | Gateway-level limits (10 MB, 30 s) still apply and use API Gateway's own bodies; our 32 KiB cap sits well below |
| Reserved concurrency 5 by default, `-1` opt-out | A hard ceiling on parallel model calls and spend. New accounts can have too low a limit to reserve any | The opt-out removes the ceiling; the guide says to record that decision |
| Lambda timeout 29 s, adapter budget 25 s, API Gateway integration timeout 29 s | HTTP API integrations are cut at 30 s and that is not adjustable (AWS HTTP API quotas) | A very slow model call returns 503 `ADAPTER_TIMEOUT` rather than hanging |
| Stage only `*.py` of `backend/`, `contracts/`, `optimizer/` into the build input | No tests, fixtures, docs, frontend, schemas or lockfiles in the package | `contracts/*.json` are not shipped (nothing at runtime reads them; a test imports the staged tree alone to prove it) |
| `deploy.ps1` refuses to package without `optimizer/api.py` unless `-AllowMissingOptimizer` | The live workflow needs the optimizer, and a stack that answers 503 on its main routes is easy to mistake for success | An early thin-slice deploy needs an explicit flag |
| `smoke.py` returns exit 4 (PARTIAL) when anything is skipped | `--skip-model` or a missing `--origin` must never be reported as full verification | A script that needs three arguments to be fully green |
| `smoke.py` uses only the standard library | No install step on the machine doing the verification | A little more code than using `requests` |

## Data flow

`deploy.ps1`: prerequisites check, stage `.aws-sam\stage\function` (source + `requirements.txt`), `sam validate --lint`, `sam build` (resolves Linux wheels), stop.
With `-Deploy`: `aws sts get-caller-identity` (identity only), typed account id, `sam deploy --confirm-changeset` (S3 upload via `--resolve-s3`, CloudFormation change set,
IAM capability), `describe-stacks` outputs.

Request path once deployed: browser (Amplify origin) to API Gateway HTTP API (throttled) to Lambda `backend.app.lambda_handler` (reads `ALLOWED_ORIGIN`, `BEDROCK_MODEL_ID`, `COMMIT_SHA`, ...) to
`App.handle` (B1 to B5 pipeline) to optimizer (in the package) and, for extract/explain/proposal, Bedrock `Converse` in the same region using the execution role. Errors use the one envelope.

## Judge questions with grounded answers

1. **How do you make sure the cloud deployment can't be abused for cost?** Layers that are all in the template: reserved concurrency (5), HTTP API throttles (5 req/s, burst 10), a 32 KiB request cap, a token cap per model call, at most two model calls per request,
   an in-flight cap per container, and a log retention limit. Budget alerts are only warnings. The honest limit is that none of it has been load-tested, and the public demo has no authentication.
2. **Why did you give the Lambda only `bedrock:InvokeModel` on named ARNs?** `Converse` needs that single action, and the template's pattern rejects any ARN with a wildcard, so the role cannot be widened by a typo. For an inference profile AWS also requires the foundation-model ARN in each region
   it routes to, which is why the parameter is a list and the guide calls it out.
3. **Why does CORS live in the Lambda and not in API Gateway?** One source of truth: the same code answers preflight and real requests, so they cannot disagree, and the allow-list is tested (an unlisted origin gets no header; the response never carries a credentials header). The template has no `CorsConfiguration`, and a test fails if one is added.
4. **Is it deployed? Does it work in the cloud?** No, and not verified. The template validates and builds, the artifact has the right Linux binaries and no stray files, and the deploy and smoke scripts work against a local stand-in. Whether a stack deploys, Bedrock answers from Lambda, and the hosted browser flow works can only be shown by running `deploy.ps1 -Deploy` then `smoke.py` with real access.
5. **What stops someone from deploying by accident, or to the wrong account?** `deploy.ps1` stops after the build unless `-Deploy`, never guesses a region, prints the account id and makes you type it, and `sam deploy` shows the change set before executing it. Tests prove the script cannot reach an AWS call without those steps.
